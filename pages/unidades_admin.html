Nivel I · Santuario

Fundamentos de Arquitectura de Software

La arquitectura de software es el conjunto de estructuras necesarias para razonar sobre un sistema: elementos, relaciones entre ellos y propiedades de ambos. No se limita a un diagrama bonito: captura decisiones tempranas que son costosas de revertir, define límites de módulos y establece cómo el software cumplirá atributos de calidad como disponibilidad, seguridad, modificabilidad y desempeño. Principios como separación de intereses, alta cohesión, bajo acoplamiento, encapsulamiento y diseño dirigido por responsabilidad evitan que el sistema se convierta en un “boss” imposible de mantener.

Un estilo arquitectónico (capas, cliente-servidor, pipes and filters, microservicios, event-driven, hexagonal) describe una familia de sistemas con las mismas restricciones. Un patrón resuelve un problema recurrente dentro de ese estilo: Broker, MVC, CQRS, Circuit Breaker o API Gateway. Elegir estilo y patrón implica trade-offs: lo que ganas en escalabilidad puedes perderlo en consistencia o complejidad operacional. El arquitecto documenta esas decisiones (ADRs) para que el equipo no vuelva a pelear la misma batalla sin memoria histórica.

Nivel II · Forja

Modelado POO, componentes, capas y UML

El modelado orientado a objetos traduce el dominio en tipos con estado y comportamiento. Clases, interfaces, herencia y composición no son adornos de lenguaje: son herramientas para localizar el cambio. Un componente bien diseñado expone un contrato estable y esconde su implementación. La arquitectura en capas (presentación, aplicación, dominio, infraestructura) organiza esas piezas para que las reglas de negocio no dependan de frameworks ni de detalles de persistencia.

UML sirve como lenguaje compartido: casos de uso para el perímetro funcional; diagramas de clases para estructura; secuencia y comunicación para colaboración temporal; componentes y despliegue para la vista de runtime. El error clásico es dibujar UML después de programar. El valor aparece cuando el diagrama guía interfaces, paquetes y pruebas, y cuando se mantiene lo suficientemente abstracto como para no romperse con cada refactor menor.

Nivel III · Puentes

Comunicación, APIs e integración

Los sistemas reales casi nunca viven solos: conversan con pasarelas de pago, IoT, ERPs y clientes móviles. Una API es el contrato de esa conversación. REST enfatiza recursos, verbos HTTP y códigos de estado; GraphQL permite consultas selectivas; gRPC destaca en comunicación interna de baja latencia. Independientemente del estilo, hay que versionar, autenticar, limitar tasa, idempotencia y documentar esquemas (OpenAPI). El diseño de interfaces incluye tanto el contrato técnico como la experiencia del consumidor: nombres predecibles, errores accionables y paginación.

La transmisión de datos exige pensar en formato (JSON, Protobuf, Avro), serialización, compresión y semántica de entrega (at-most-once, at-least-once, exactly-once). Colas y buses desacoplan productores y consumidores; webhooks y SSE cubren eventos hacia el borde. Integrar también es fallar con dignidad: timeouts, reintentos con backoff, circuit breakers y DLQ evitan que un servicio caído contagie a todo el reino.

Nivel IV · Ciudadela

Frameworks, estándares y optimización

Un framework de arquitectura (TOGAF, C4, 4+1 de Kruchten, arc42) no escribe el código por ti: organiza vistas, stakeholders y gobernanza. Los estándares —ISO/IEC 25010 para calidad, 12-Factor para cloud, OWASP para seguridad, convenciones de logs y métricas— reducen la variabilidad inútil. Las buenas prácticas incluyen infraestructura como código, pipelines CI/CD, feature flags, observabilidad (trazas, métricas, logs) y pruebas de arquitectura (ArchUnit, fitness functions) para que las reglas no se diluyan con el tiempo.

Optimizar no es “hacer más rápido a ciegas”. Primero se mide: cuellos de CPU, I/O, N+1, chatty APIs, cold starts. Luego se aplican cachés, índices, asincronía, particionado y backpressure. El arquitecto equilibra costo, complejidad y beneficio: una micro-optimización que rompe claridad suele ser una trampa. El cierre del curso es convertir principios en un sistema operable, documentado y listo para evolucionar sin reescribir el mapa cada semestre.
